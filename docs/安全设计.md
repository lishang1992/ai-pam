# AI 安全堡垒机 V1 —— 安全设计说明

面向安全评审 / 技术尽调：把「为什么这样设计」和「代码在哪一行」对齐，便于逐条验证。

---

## 1. 威胁模型：AI 时代的四类新风险

| 风险 | 传统堡垒机 | AI 场景新增的难点 | V1 的应对 |
| --- | --- | --- | --- |
| 身份不可知 | 人有账号 | 「AI 是谁」没有身份概念 | Agent 作为一等身份：模型 / 工具白名单 / 资产 / 授权用户 |
| 权限失控 | 按人授权 | 模型可能被诱导提权 | 双层授权：Agent 权限 ∩ 用户权限，任一不满足即拒绝 |
| 不可控执行 | 人敲命令 | 模型直接生成 shell 无法审计 | 取消自由 shell，只允许结构化 Tool + 固定命令模板 |
| 不可追溯 | 命令历史 | Prompt 与工具链脱节 | Session 维度串联 Prompt / Tool / 风险 / 审批 / 命令 / 结果 |

---

## 2. 核心结论：AI 只有建议权

```
AI 层（ai/runner.py, ai/planner.py, ai/llm.py）
   └── 只能产出：{"kind": "tool", "tool": ..., "arguments": {...}}
                     ↓
安全网关（security/gateway.py::authorize）  ← 唯一的放行判定
                     ↓
人工审批（security/approvals.py）           ← 高风险必须人工介入
                     ↓
执行代理（proxy/ssh_proxy.py::execute）     ← 只有这里能碰目标机
```

代码里不存在任何「AI 直接执行」的路径：`gateway.execute()` 只被 `runner._execute_step()` 调用，
且调用前必须拿到 `decision == ALLOW` 或 `APPROVAL → approved`。

## 3. 五条安全原则的实现

### 原则一：AI 没有最终执行权

- 工具调用必须经过 `gateway.authorize()`，返回 `ALLOW / APPROVAL / DENY`；
- `DENY` 时命令**不会**下发，AI 只收到拒绝原因，并被迫改用其他方案或直接给结论。

### 原则二：Agent 权限不能超过用户权限

`gateway.authorize()` 中五项校验全部通过才继续：

```python
agent_enabled       Agent 必须处于启用状态
user_agent_grant    用户被授权使用该 Agent
agent_tool_grant    工具在 Agent 白名单内
agent_asset_grant   资产已授权给 Agent
user_asset_grant    用户本人拥有该资产权限     ← 关键：Agent 无法放大用户权限
```

验证脚本场景 4 就是这条原则的回归测试。

### 原则三：高风险操作脱离 AI 自主决策

- 风险等级由 `security/risk.py` **规则化**计算，可解释、可复现，不交给大模型自证清白；
- 两道硬约束（可在 `settings.py` 调整）：
  - `RISK_ESCALATE_TO_APPROVAL_AT=HIGH`：策略放行但风险达阈值 → **强制转人工审批**；
  - `RISK_BLOCK_AT=CRITICAL`：风险达阈值 → **直接拒绝，审批也无法绕过**；
- 审批默认 900 秒超时，超时按拒绝处理并留痕。

### 原则四：所有 AI 操作可追溯

每个环节都写 `audit_events`（同时落 `data/audit/<会话编号>.jsonl`，只追加不覆盖）：

```
session_created → prompt_received → ai_tool_request → risk_assessment →
policy_decision → approval_requested → approval_decided → tool_executed →
ai_analysis → session_finished
```

审计记录包含当时的**完整判定依据**：五项权限校验结果、风险原因、命中策略、实际命令、耗时、退出码、输出摘要。
导出接口：`GET /api/audit/sessions/{id}/export?format=json|csv`。

### 原则五：会话结束后临时权限立即失效

`runner.finish_session()`：把所有 `pending` 审批置为 `expired`、终止运行中的任务、写入 `ended_at`。
被强制终止的会话同样留审计（`session_terminated`）。

## 4. 命令注入防护（为什么不能拼 shell）

1. `backend/config/tools.yaml` 定义每个工具的参数类型与正则白名单，例如服务名 `^[A-Za-z0-9_.@-]+$`；
2. `ai/tools.py::validate_arguments()` 拒绝未知参数、非法字符，并对长度与数值范围设限；
3. 命令由**固定模板**渲染（`command_template`），AI 只能填参数、不能改命令结构；
4. `proxy/ssh_proxy.py::check_command_safety()` 兜底拦截危险 shell 组合；
5. 凭据只从环境变量读取（`credential_ref` 存的是变量名），数据库里没有明文口令与私钥。

   凭据取值顺序：**环境变量 > 本地凭据库 `data/secrets.json`（权限 600）**；
   写文件类工具（`modify_config`）的内容用 base64 传输，避免引号/换行造成的注入。

## 4.1 角色与权限边界

三种角色在**界面与接口两层**同时生效（前端隐藏 + 后端 `require_role` 校验，绕过前端也没用）：

| 能力 | 运维人员 | 安全管理员 | 审计管理员 |
| --- | --- | --- | --- |
| 创建会话 / 下达 AI 任务 | ✅ | ✅ | ⛔ 403 |
| 查看会话 | 仅自己的 | 全部 | 全部（只读） |
| 审批高风险操作 | 自己发起的 | 全部 | ⛔ |
| 强制终止会话 | 仅自己的 | 全部 | ⛔ |
| 新增/修改/删除资产 | ⛔ 403 | ✅ | ⛔ 403 |
| 修改 Agent 授权 | ⛔ 403 | ✅ | ⛔ 403 |
| 修改策略规则 | ⛔ 403 | ✅ | ⛔ 403 |
| 导出审计报告 | 自己的会话 | 全部 | 全部 |

真实 Linux（SSH）纳管能力：

* 支持 `ssh` 执行器，认证方式支持**私钥**（ed25519 / ecdsa / rsa）与**口令**（paramiko 或系统 ssh 回退）；
* 新增资产时自动做连通性测试（真的登录并执行 `uptime`），失败会明确报错而不是假装成功；
* 真实主机的命令输出会被 `proxy/parsers.py` 解析为结构化指标（CPU/内存/磁盘/服务状态/日志错误数），
  风险引擎与最终结论都基于这些真实数据，而不是模型复述文本。

## 5. 默认策略基线（开箱即用）

| 策略 | 作用域 | 优先级 | 典型规则 |
| --- | --- | --- | --- |
| Global Guardrails | global | 500 | `delete_file=DENY`、`export_database=DENY`、`stop_service=APPROVAL` |
| Production Protection | env=production | 200 | 只读 `get_*=ALLOW`；`restart_service/stop_service/modify_config=APPROVAL`；`install_package/delete_file/export_database=DENY` |
| Test Environment Relaxed | env=test | 100 | `*=ALLOW`；`restart_service/stop_service/modify_config=APPROVAL`；`delete_file/export_database=DENY` |

判定顺序：**资产 > Agent > 环境 > 全局**，同层级 `DENY` 永远胜出；
未命中任何规则时采用保守默认（只读放行，变更类转审批）。

## 6. 数据模型（11 张表）

```
users ─┬─ user_agents ── agents ─┬─ agent_tools ── tools
       ├─ user_assets ── assets ─┴─ agent_assets
       └─ sessions ─┬─ messages
                    ├─ tool_calls ── approvals
                    ├─ risk_events
                    └─ audit_events
policies ── policy_rules
```

- `tool_calls` 是「一次工具调用的一生」：参数、原因、风险、策略、命令、状态、结果、耗时；
- `approvals` 记录审批人与意见，供事后追责；
- `risk_events` 单独成表，便于统计「风险阻断 / 高风险事件」等安全指标。

## 7. 上线前必须做的加固（V1 之外）

1. 替换 `AIB_SECRET_KEY`，启用 HTTPS，接入企业 SSO / MFA；
2. SQLite 换 PostgreSQL，事件总线换 Redis/NATS，支持多实例与高可用；
3. 审批人改为角色 + 值班表 + 多级会签，审批请求推送企业 IM；
4. 审计日志写入只追加存储（对象存储 + WORM）并做哈希链防篡改；
5. 接入企业资产中心 / CMDB，资产与授权由外部系统同步；
6. 增加 Prompt 注入检测模型与会话级异常行为检测（例如同一会话突发大量高危请求）。
